### 診断結果

```
考察力: ○ 方針は見える
典型知識: ○ 星4以下は定着している
実装設計力: × ← ボトルネック
```

**症状:**
- 方針は見えるのに実装でぐちゃぐちゃになる
- 条件が複雑になると整理できない
- 詰めて実装するのに時間がかかりすぎる
- 本番の調子に左右される（実装がうまくいくかは運次第）

**根本原因:**
「方針→コード」の変換プロセスが確立されていない。
頭の中で考えながら書くため、複雑になると破綻する。

## 戦略: 実装設計力の強化

### 核心: 「書く前に設計する」習慣をつける

今の問題は「考えながら書いている」こと。
**書き始める前に設計を終わらせる**ことで、実装の安定性が劇的に上がる。

---

## Phase 1: 実装設計プロセスの確立（1-2ヶ月）

### 新しい解き方フロー

```
1. 問題を読む（2分）

2. 考察フェーズ（10-15分）
   - 制約から計算量を逆算
   - 使えそうなアルゴリズム/データ構造を列挙
   - 方針を決める

3. ★設計フェーズ★（5-10分）← これが新しい
   - 入力の受け取り方
   - 主要な変数/配列の定義
   - 処理の流れを箇条書き（日本語で）
   - 関数に切り出す部分を決める
   - エッジケースを列挙

4. 実装フェーズ（15-20分）
   - 設計に従って書くだけ
   - 迷ったら設計に戻る

5. デバッグ（5分）
   - サンプル確認
   - エッジケース確認
```

### 設計フェーズの具体例

**例: ABC444-C（棒菓子問題）**

```
【方針】
Lの候補を絞って全検証

【設計メモ】
入力: N, A[N]
出力: 条件を満たすLのリスト

Lの候補:
- A[i] そのもの（分割なし）
- A[i] + A[j] の組み合わせ（分割あり）
→ 候補は高々 N + N^2 個だが、setで管理

検証関数 check(L):
  - 各A[i]について:
    - A[i] == L → OK（そのまま）
    - A[i] < L かつ (L - A[i]) が配列に存在 → OK（ペア）
    - それ以外 → NG
  - 全部OKならtrue

注意:
- 同じ値が複数回使われる場合のカウント
- A[i] == L/2 の場合、2個以上必要

【関数分割】
- main: 入力、候補列挙、出力
- check(L): 検証ロジック
```

**この設計を書いてから実装に入る。**

**ポイント:** 解法は分かっているので、「設計→実装」の変換を練習する。

### 方法2: 新しい問題で設計フェーズを強制する

1問解くたびに、**コードを書く前に設計メモを書く**。
最初は時間がかかるが、慣れると逆に速くなる。

### 方法3: 他人のACコードを「設計視点で」読む

AtCoderの上位者のコードを見て：
- どう関数分割しているか
- 変数名のつけ方
- ループの回し方

を観察する。

## コンテスト中の行動指針

### C問題で詰まったときのチェックリスト

```
□ 方針は明確か？（曖昧なまま書き始めていないか）
□ 設計メモを書いたか？（頭の中だけで考えていないか）
□ 変数/配列の役割は明確か？
□ ループの範囲は正しいか？
□ エッジケースを考えたか？
```

### 実装が崩れそうなときの対処

1. **一度手を止める**（焦って書き続けない）
2. **今何をしようとしているか言語化**
3. **紙に処理の流れを書く**
4. **簡単なケースでシミュレーション**
5. **それから書き直す**
