|---|---|---|---|

→ 入出力を 1 行短くするだけのマクロは、使える状態でも手書きの癖に負けている。

## 3. 提案（効果が大きい順）

### A. ローカルのビルドで UBSan を有効にする（ツール）
- 根拠: オーバーフロー 2 件（abc246_d、abc242_d）。abc246_d は原因が特定できず、python に書き直した。
- 確認済み: 手元の g++-16 で `-fsanitize=undefined` を付けると、`long long` の乗算のオーバーフローを
  `runtime error: signed integer overflow` として報告した。`-fno-sanitize-recover` を併用すると、その時点で止まって終了コードが ≠0 になる。
  配列外参照は、libstdc++ の既定のアサーションで既に止まる（abc267_d の assert）。`-ftrapv` は反応しなかったので使わない。
- 入れる場所: `scripts/build.py` の `CXXFLAGS` に足す（ローカル実行だけに効き、提出コードには影響しない）。
- 未確認: プリコンパイル済みヘッダ（template.hpp.gch）が同じフラグで作り直されるか。実行速度の低下。

### B. テンプレートに高速 IO を入れる（テンプレート）
- 根拠: `endl` の毎行フラッシュが TLE の要因になった（abc212_f、abc213_c）。旧解答の 93 ファイルが `cout << x << endl` の形で出力していた。
- 案: template.hpp に「静的初期化で `ios::sync_with_stdio(false); cin.tie(nullptr);` を呼ぶ」1 行を足す。
  `#define endl '\n'` まで入れるかは選ぶ必要がある（入れるとインタラクティブ問題では `cout << flush` を手で書くことになる）。

### C. ストレステストの雛形（スクリプトまたはスニペット）
- 根拠: `デバッグ` 7 件。abc267_d では愚直解を書いて回す準備に時間がかかった。ea57d10 時点の main.cpp には、ストレステストのループがコメントアウトされたまま残っている。
- 案: `scripts/stress.py`（`brute.cpp` と `main.cpp` を、`gen.py`（または `random.cpp` を使った生成器）の入力で N 回比較し、
  最初に一致しなかった入力を `honban/in` に書き出す）。精進パネルのタスクから呼べるようにする。
- 1 章の結論に照らすと、マクロではなく「1 コマンドで回る」形でないと使われない。

### D. `rect_sum` の引数を、軸ごとの区間の順に揃える（既存ライブラリの変更）
- 根拠: abc311_e で、本人が自然に書いた順番は `(行の始点, 行の終点, 列の始点, 列の終点)` だった。
  単体テストも同じ順番で書いたため、ライブラリのバグだと誤認して約 2 分（15:38〜17:36）を使った。
- 案: `rect_sum(s, x1, x2, y1, y2)` に変える。今の呼び出し箇所は abc311_e.1.cpp だけ。
  ほかの区間を受け取るライブラリ（セグ木の `get(l, r)` など）の引数の順番とも揃える。

### E. DP 雛形の「未計算」と「到達不能」を分ける（優先度は低い）
- 根拠: abc301_e（`inf` を未計算の目印にしたため、到達不能の状態と区別できなかった）、abc267_d（初期値の −inf と 0 の境界があいまい）。
- 案: メモ化再帰のスニペットでは、「計算済みか」を値とは別の `vb` で持つ形を雛形にする。件数は 2 件なので、再発したら作る。
