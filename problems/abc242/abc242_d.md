## 問題

`A`, `B`, `C` のみからなる文字列 S が与えられる。S^(0) = S とし、i = 1, 2, 3, ... について、
S^(i-1) の各文字を同時に次のように置き換えたものを S^(i) とする。

- `A` → `BC`
- `B` → `CA`
- `C` → `AB`

Q 個のクエリに答えよ。i 番目のクエリでは、S^(t_i) の先頭から k_i 文字目を出力する。

**入力**

```
S
Q
t_1 k_1
⋮
t_Q k_Q
```

**出力**

各クエリの答えを 1 行ずつ出力する。

**制約**

- S は `A`, `B`, `C` のみからなる長さ 1 以上 10^5 以下の文字列
- 1 ≤ Q ≤ 10^5
- 0 ≤ t_i ≤ 10^18
- 1 ≤ k_i ≤ min(10^18, |S^(t_i)|)
- 入力はすべて整数（S を除く）

**自分の考察**

長さが倍々になるので、1文字が 10^18 を超えるまでの分岐は最大60回程度。セグメント木を降りるときのように、
k がどちらの子に入るかで分岐していけばよいと考えた。i 文字目の担当範囲は [i·2^t, (i+1)·2^t)。
t が大きいときは、最初は無理やり t=60 に畳めばいいと思っていたが、そうではなく、
高さ60になるまで左に潜り続ける（max(0, t−60) 回左に潜ってから分岐を始める）のだと気づいた。
方針はここまで自力で立ったが、実装のバグが取れず、修正は Claude にやってもらった。

（解説後の理解）深さHの完全二分木の葉はH桁の二進数と対応していて、上位ビットからの01を見れば通ったパスがわかる。
（葉は左から 0-indexed で番号を振り、0=左の子・1=右の子。逆に、通ったパスの 0/1 を上から並べれば葉の番号になる）

**問題の核**

S^(t) は S の各文字を根とする高さ t の完全二分木の葉の列。k < 2^60 なので、t > 60 なら根は s[0] で、
最初の t−60 段は必ず左へ進む。左の子は文字 +1、右の子は +2（mod 3）なので、
答えは `s[k >> t] + t + popcount(k の下位 t ビット)`（mod 3）と閉じた式にもなる。

**会話から残すこと**

- 「巨大な t は小さい値に畳む」ときは、畳んだ部分が答えに与える影響（ここでは左に潜る回数 t−60 → 文字が (t−60) mod 3 ずれる）を必ず残す。値を切り詰めるだけでは答えが変わる。
- 二分木を降りるときは、区間 [l, r) と k を **同じ座標系**（全体の絶対位置か、ブロック内の相対位置のどちらか）で持つ。片方だけオフセットを引くと比較がずれる。
- 子の選び方は、mid と k の比較から「k < mid → 左（r = mid）」と一度書き下してから実装する。l / r の更新と左右の対応を逆にしやすい。
- 「左右のどちらかで値が決まる＝加算でまとまる」と気づけば、降下ループは popcount に置き換えられる（ループは O(t)、閉じた式は O(1)）。
- **完全二分木上の根→葉のパス と t 桁の二進数 は一対一対応**（本人の言葉:「t桁の二進数みたいになっている」）。左から k 番目（0-indexed）の葉への道順は k の上位ビットから「0=左, 1=右」。深さ d の節は k の上位 d 桁に対応し、区間 [l, r) を半分にする降下はこれを区間で書いたもの。ビットを直接見れば座標系の取り違えが起きない。
  - t > 60 で「t−60 回左に潜る」のは、k < 2^60 を t 桁で書くと上位 t−60 桁が全部 0 だから。
  - セグ木の配列表現（節 i の子が 2i, 2i+1。節番号の二進数＝先頭の 1＋根からの道順）、ダブリングで k 回先をビット分解する処理（abc212_f）も同じ対応に基づく。
- 文字の巡回ずらしは library/util/shift_char.cpp（本問を機に作成）。`get_l` = `shift_char(f, 1, 'A', 3)`、`get_r` = `shift_char(f, 2, 'A', 3)`。

**難所**

- 考察: 当初は「t ≥ 60 なら t=60 に畳む」とだけ考えていたが、それだと根の文字が s[0] から (t−60) mod 3 ずれる分が抜ける。29:24 に自分で「max(0, t−60) 回左に潜る」と修正した。
- 初回実装（21:54 版）には次の3つのバグがあり、サンプルが合わなかった:
  1. `k -= l*(1LL << t)` で k はブロック内の相対位置にしたのに、区間の左端 `l` は **文字番号のまま**（`r = (l+1)<<t` は絶対位置）。区間と k の座標系が揃っていない。
  2. `if(k < mid)` で `l = mid`（右半分へ進む）にしたうえで `get_l`（左の子）を適用していた。比較結果と進む向きが逆。
  3. t ≥ 60 の畳み込みが入っておらず、t が大きいと `1LL << t` がオーバーフローする。また l を線形に探すループ `while((l+1)*(1LL<<t) <= k) l++` は t=0 で O(|S|) になる。
- 修正版（Claude と作成）: `l = k / 2^t` で文字番号を求め、`l = l·2^t` で絶対座標に揃え、`mid <= k` なら右（`get_r`）に進む。t > 60 なら `get_l_many(s[0], t−60)` で根の文字を畳む。

**レビュー(LLM)**

1. **考察の評価** — 重要な制約（k ≤ 10^18 < 2^60）から「分岐は60段で足りる」を 04:42 に導けており、方針を決めた根拠は言語化できている。足りないのは、(a) t > 60 のとき k < 2^60 より文字番号が必ず 0 になる（＝根は s[0]）という一文、(b) 左の子＝+1、右の子＝+2 という置換規則の言い換え。(b) があれば、畳み込みの影響（t−60 回の +1）も、降下を popcount に置き換えることも同じ観察から出てくる。
2. **弱点・思考の癖の指摘** — つまずき分類 `実装バグ` はこれで6件目（abc212_f, abc213_d, abc246_d, abc267_d, abc481_f, 本問）。そのうち `解説AC` になったのは abc212_f・abc481_f・本問の3件で、いずれも **方針は自力で正しく、AC が実装修正への依存で決まった**。原因はどれも境界・座標の取り扱い（abc212_f の境界処理、abc246_d のオーバーフロー、abc267_d の初期値の境界、本問の座標系の混在と左右反転）。「方針が立つと、区間・座標の不変条件を書かずにすぐ実装に入る」のが繰り返し出ている癖。実装前に `[l, r) は絶対座標、k も絶対座標、k < mid なら左` のような不変条件をコメントで1行書くと、この型のバグを直接防げる。
3. **別解・より良い方針** — 想定解は再帰 `f(t, k) = next(f(t−1, k/2), k mod 2)`。さらに左＝+1・右＝+2 なので、答え＝`(s[k>>t] − 'A' + t + popcount(k & (2^t − 1))) mod 3`。t ≥ 60 では `k>>t = 0`、mask = k とすれば畳み込みの場合分けも要らない（t mod 3 で吸収）。1クエリ O(1)。
4. **実装の正しさ・計算量** — 最終版は正しい。O(Q · min(t, 60))。`(l+1)·2^t ≤ k + 2^t ≤ 10^18 + 2^60` なので、r と `l+r` はオーバーフローしない。気になる点: `cout << endl` を 10^5 回呼んでいる（abc212_f で `定数倍高速化` が付いたのと同じ形。今回は間に合うが `'\n'` にする）。`ll cnt` が未使用。`get_l_many` の9分岐は `'A' + (c − 'A' + n) % 3` の1行で書ける。

## 問題全体のメモ

- 別解（O(1)）: `char ans = 'A' + (s[t >= 60 ? 0 : k >> t] - 'A' + t % 3 + popcount(t >= 60 ? k : k & ((1LL << t) - 1))) % 3;`（k は 0-indexed）
- 「各要素が2つに増殖する文字列の k 番目」は、完全二分木を根から降りる / 葉から親へ遡る型。ダブリングや二分探索で根から降りる処理（abc212_f）と同じ「区間を半分にしていく」操作。
