## 問題

長さ N の数列 A = (A_1, …, A_N) が与えられる。Q 個のクエリを順に処理する。各クエリは次のいずれか。

- `1 x` : A のすべての要素を x で置き換える。
- `2 i x` : A_i に x を加える。
- `3 i` : A_i の値を出力する。

**入力**

```
N
A_1 A_2 … A_N
Q
query_1
⋮
query_Q
```

各 query_q は `1 x`、`2 i x`、`3 i` のいずれかの形式。

**出力**

3 番目の形式のクエリの個数を X として X 行。j 行目に j 番目の 3 番目形式のクエリの答えを出力する。

**制約**

- 1 ≤ N ≤ 2×10^5
- 1 ≤ Q ≤ 2×10^5
- 0 ≤ A_i ≤ 10^9 (1 ≤ i ≤ N)
- 2 番目または 3 番目の形式のクエリでは 1 ≤ i_q ≤ N
- 1 番目または 2 番目の形式のクエリでは 0 ≤ x_q ≤ 10^9
- 3 番目の形式のクエリが少なくとも 1 つ存在する
- 入力される値はすべて整数

**問題の核**

全体代入を即座に N 要素へ反映せず、「最後の全体代入の値と時刻」だけを持つ。各要素は自分の最終更新時刻を持ち、
アクセス時に「自分の時刻 < 全体代入の時刻」なら全体代入の値で上書きしてから操作する（遅延反映）。

**難所**

- type1 を「全体加算」と誤読し、abc212_d 型の基準点オフセット（`b += x`, 出力 `a[i]+b`）で一度実装した。全体加算と全体代入は解き方が別物になる。
- type3 の入力を `cinll(i, x)` と type2 からコピーしたまま書き、余計に1つ読んで入力がずれた（デバッグ出力で特定）。
- タイムスタンプ方式に書き直した際、type2 で加算した要素の時刻 `a[i].snd = m` の更新を書き忘れた。全体代入後に個別加算した値が、次のアクセスで全体代入の値に巻き戻される。

**レビュー(LLM)**

1. **考察の評価** — 正しい方針（値と時刻の組を持ち、アクセス時に時刻比較で遅延反映）は 05:54 のログに1行で言語化されている。
   不足は2点。(a) 誤読にどう気づいたか（サンプル不一致か再読か）が無い。誤読の再発防止を検討する材料になるので1行残す価値がある。
   (b) 「書き込みをした要素は時刻も更新する」という不変条件（各要素の時刻＝その値が最後に確定した時刻）が言語化されておらず、実際に抜けた。
   タイムスタンプ方式では「何の時刻を持つか」を1行で定義してから書くと、更新漏れを防げる。
2. **弱点・思考の癖** — 誤読はつまずき分類の統制語彙に無いため実装バグ以外を付けていないが、記録上2例目（abc213_f の考察ノート「問題を誤読していた。求めるのは各 k について Σ…」）。
   今回は誤読先が既知の型（abc212_d の全体加算オフセット）で、既に解いた型に引き寄せて読んだ形。まだ語彙追加の根拠としては件数が足りないので、再発したら「読解」をつまずき分類に追加する候補として扱う。
   実装面は、似た分岐のコピーで入力の読み数を誤る（type3 に x）、状態更新の一部漏れ、と「分岐ごとの入出力・更新の差分チェック不足」の形。
3. **別解・より良い方針** — 時刻を使わない別解: 全体代入時に「前回の全体代入以降に個別加算された添字」を記録しておき、代入時にそれらだけ加算分を 0 に戻す。
   各要素の値を「ベース値 b ＋ 個別加算 add[i]」で持ち、type1 で b=x にしつつ触った添字の add を 0 にリセットする（添字の記録は個別加算の回数分しか溜まらないので償却 O(N+Q)）。
   時刻比較は不要になるが、本解（タイムスタンプ）の方がクエリごと O(1) で単純。初期値を「時刻 0 の値」として扱える点も本解の利点。
4. **実装の正しさ・計算量** — 最終コードは正しい。O(N+Q)。初期 a の時刻 0、b の時刻 -1、クエリ時刻 m は 1 始まりなので、全体代入前は a が優先、代入後は b が優先で順序関係に問題なし。
