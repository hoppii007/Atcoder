# 本番レビュー → ノート記録

精進パネル（VSCode 拡張 `vscode-extension/`）で解き終えて「記録する」を押した問題を、
問題文・実装・本人の考察・会話を突き合わせてレビューし、`problems/<contest>/<task>.md` に
**第N回** として記録する手続き。

前提となる仕様（ノート/タグのフォーマット、`solved` の定義、弱点分析の方針）は
プロジェクトルートの `CLAUDE.md` に従う。この skill はその「実行手順」を担う。

**記録は客観的事実だけで作る。** 体感（felt）のような主観の評価は記録しない。

## トリガー

本人が「**レビューして**」「**終わりました。レビューして**」（同義の依頼を含む）と言ったとき、または `/honban-review`。
**それ以外のタイミングでレビューを先回りしない。**

## 入力（4つ）

1. **`honban/.session.json`** — 精進パネルが「記録する」で書き出す。欄:
   ```
   task_id         … 例 "abc318_f"（対象ノートの特定に使う）
   contest_id      … 例 "abc318"
   url             … 問題ページ
   note_path       … 例 "problems/abc318/abc318_f.md"
   date            … 解き始めた日時（YYYY-MM-DD HH:mm。旧形式の session は YYYY-MM-DD のみ）
   difficulty      … AtCoder Problems の値（無ければ null）
   solved          … 自力AC / 解説AC / 未AC（本人がパネルで選んだもの）
   time_spent_min  … タイマーの値（本人が修正した場合はその値）
   thought_log     … 思考ログ [{elapsed: "mm:ss", text}]。解いている間に本人が書き足した原文（elapsed はタイマーの経過時間）
   self_notes      … （旧形式の session のみ）単一テキストの考察メモ。あれば thought_log の代わりに使う
   code_history_dir … 例 "honban/.history/abc318_f"（スナップショットの置き場所）
   code_timeline   … コードの推移 [{elapsed, event, file, exit?}]（旧形式の session には無い）
   ```
2. **`honban/main.cpp`** — 実装。`#include "library/..."` があれば、その library ファイルも読んで
   実装の一部として扱う（どのライブラリを使ったかもレビュー・タグ付けの材料になる）。
3. **コードの推移**（`code_timeline` と `code_history_dir` 以下の `NNN.cpp`）— 区切りの操作ごとの main.cpp。
   `event` は `start`（解き始め＝テンプレート）/ `save` / `log`（思考ログを書いた時点のエディタの内容）/
   `build` / `input` / `run` / `expand` / `submit`（タスク終了。`exit` が終了コード、`build` の exit≠0 はコンパイルエラー、
   `input`/`run` の exit≠0 は実行時エラー）/ `finish`（解き終わり）。同じ `file` を指す行は内容が変わっていない。
4. **この会話** — 解いている途中・解いた後に Claude と話した内容（WA の原因、指摘、出てきた知見など）。
   「問題の核」「会話から残すこと」「難所」の素材になる。

## 手順

### 1. 読む
`honban/.session.json` を読む。**無い・または会話で話している問題と task_id が食い違う場合は、
記録せずに本人に確認する**（パネルで「記録する」を押し忘れている可能性がある）。
`honban/main.cpp` を読む。問題ページ（`url`）を **WebFetch で取得**する。レビューのために
制約・入出力を確認するのに加え、新規ノートを作る場合（手順5）は問題文・制約の記入に使う。

### 2. 思考ログを分析する（本人と下書きを詰める工程は無い。止まらずに手順3へ）
解いている間、本人は Claude に答えを求めず、思考ログに時刻つきで書き足している。
本人の言葉は思考ログ（原文）にそのまま残るので、「自分の考察」をまとめ直す工程は置かない。
代わりに Claude がログを分析し、ノートの **思考ログの分析** に残す。書くこと:

- **時間配分** — 読解・方針決定・実装・デバッグにそれぞれ何分使ったか（ログの時刻から）。
- **到達点** — どの時点で何が正しく立っていたか（状態定義・計算量見積もりなど）、どこから外れたか。
  正解と照らして、ログのどの記述が合っていて、どの記述（またはどの欠落）が詰まりの原因かを特定する。
- **自己診断の精度** — 本人が詰まりの原因をログ上で言い当てていたか、それが修正に結びついたか。
- **本人の自己言及** — 「いつもここでつっかえる」のような癖への言及があれば拾い、過去ノートの記録と照合する。

ログと実装・会話が食い違う点は、推測で埋めずに「ログからは不明」と書く。
`thought_log` が空なら、その旨を書き、実装・会話から分かる範囲だけを分析する。

### 2.5 コードの推移を分析する
`code_timeline` があれば、`file` が変わる境目ごとに隣り合うスナップショットの差分を読む
（`git diff --no-index --stat` で変化量を見てから、必要な箇所だけ `git diff --no-index -U1 A B`）。
全スナップショットを全文読まない。ノートの **実装の推移の分析** に残す。書くこと:

- **実測の時間配分** — 書き始め（start から最初に中身が変わった時刻）、最初のビルド成功、最初の input/run、
  最後の変更の時刻。手順2の「ログから推した時間配分」と食い違えば、こちらの実測を優先して両方を書く。
- **ビルド・実行の失敗** — コンパイルエラー（build exit≠0）と実行時エラーの回数・時刻、そのとき何を直したか（差分から）。
- **方針転換・書き直し** — 大きく消して書き直した箇所。思考ログにその転換が書かれているか。
- **ログとコードのずれ** — ログで方針を決めた時刻と、それがコードに現れた時刻の差。ログに無い変更（無言の修正）。
- **ライブラリの変更** — 解いている間に library/ を直した形跡があれば（スナップショットは main.cpp だけなので、
  `git diff` の作業ツリー差分と会話から）。

数値は推測で埋めない。`code_timeline` が無い・1件しか無いなら「記録なし」と書いて飛ばす。

### 3. レビューを書く（4点必須）
問題文・実装・思考ログ（とその分析）・会話を突き合わせ、次の4点を必ず含める:

1. **考察の評価** — 思考ログ（とコードの推移）に、鍵となる制約・語句・方針の決め手が言語化されているか（CLAUDE.md 目的#3）。
   薄ければ具体的に何を補うべきか。
2. **弱点・思考の癖の指摘** — 難所/つまずきを過去ノートの記録と突き合わせ、繰り返し現れる
   弱点パターンとして言語化する（目的#1）。根拠となるノートを示す。
3. **別解・より良い方針** — 想定解や、よりシンプル/高速な別解があれば提示。
4. **実装の正しさ・計算量** — `int main` を読み、バグ・エッジケース・計算量・可読性を指摘。
   問題なければ「問題なし」と明記。途中のスナップショットで起きた誤り（後で直したもの）は、
   最終コードの指摘と分けて「推移で直した誤り」として書く。

印象論・励まし・主観的コメントは書かない。事実と、そこから論理的に導ける指摘のみ。

### 4. タグを付ける（2軸）

**(a) 問題タグ（frontmatter `tags` / 問題レベル）** — 問題文・実装・想定解から**正式な問題タグを AI が付与する**。
手法・データ構造・考察パターンを表すタグを選び、`confidence` も判定する（典型なら `確定`、要確認なら `候補`）。
`tags.md`「問題タグ」表に無い語を使ったら、**必ず定義を1行追記**する（CLAUDE.md §3 の運用）。
- 新規ノート: AI が付けた tags / confidence を frontmatter に書く。
- 再挑戦（既存ノート）: 問題タグは問題レベルで固定。基本は維持し、明らかな誤り・不足のみ
  更新して、変更点は会話で根拠つきに述べる。無闇に付け替えない。

**(b) つまずき分類タグ（各回 `つまずき分類:` / 回レベル）** — その回の難所（会話・提出結果から分かる事実）から、
**`tags.md`「つまずき分類タグ」の統制語彙**の中で該当するものを選んで配列で付ける。
詰まり無し（自力で滞りなく解けた回）は `[]`。**この語彙は勝手に増やさない** ——
既存語で表せない詰まりが繰り返し出たときだけ、根拠つきで tags.md に1行追加する。

### 5. ノートに記録する
`note_path` を開く（無ければ `problems/_template.md` を基に新規作成）。

**新規作成時**:
- frontmatter の `id` / `title` / `url` / `difficulty` を埋める（difficulty は session の値。null なら空）。
- 「## 問題」セクションを手順1で WebFetch した問題ページから埋める（問題文の本文または忠実な要約・
  入出力の形式・制約）。制約は `N ≤ 10^5` のように原文に忠実に列挙する。取得に失敗したら空欄にせず、
  その旨を会話で伝えて手動補完を促す。
**再挑戦（既存ノートへの第N回追記）では「## 問題」と frontmatter の difficulty は書き換えない。**

既存の `### 第N回` を数えて **次の回** として末尾に追記する（古い回が上・新しい回が下）。
見出しの日付は session の `date` を**時刻まで含めてそのまま**書く（例 `### 第1回 — 2026-11-22 01:30`。
推定レートが同じ日の挑戦を解いた順に並べるのに使う）。1回分のエントリに含めるもの:

- `solved` / `time_spent_min`（session の値をそのまま）、`つまずき分類`（手順4(b)）
- **思考ログ** — session の `thought_log` を「- mm:ss 本文」の箇条書きで原文のまま転記する（書き換えない。
  複数行の本文は続く行を字下げする）。空なら「（記入なし）」。旧形式の session（`self_notes` のみ）なら省略する。
- **思考ログの分析** — 手順2で Claude が書いた分析。旧形式の session なら、代わりに **自分の考察** として
  `self_notes` を原文のまま転記する（明らかな誤字のみ直し、直した旨を会話で伝える）。
- **実装の推移の分析** — 手順2.5 の分析。`code_timeline` が無い旧形式の session なら省略する。
- **問題の核** — この問題を解く鍵になった観察・言い換えを 1〜3 行で。実装と会話から Claude が抽出する
  （例：「辺の数字は 1 以上なので桁数が少ないほど小さい → BFS の層＝桁数」）。
- **会話から残すこと** — Claude との会話で出た、今後に残すべき知見を箇条書きで。他の問題にも使える
  一般化（「この条件が揃うとこの方法が効く」）、関連する問題・ライブラリとのつながり、作った/直したライブラリなど。
  その場限りのやりとりは書かない。会話が無ければ省略してよい。
- **難所** — 会話・提出結果から分かる事実だけを書く（WA の原因、どこで何を誤ったか、反例など）。
  再現できる粒度で。詰まりが無ければ「（詰まりなし）」。
- **レビュー(LLM)** — 手順3で書いたレビュー本文。

**最終コードを残す** — `honban/main.cpp` を `problems/<contest>/<task>.<N>.cpp`（N はこの回の番号）へ
**展開前のまま**コピーする（`#include "library/..."` を残す。どのライブラリを使ったかを後で集計するため）。
未AC の回も、最後の状態をそのまま残す。ノートの本文にコードは貼らない。

`solved` / `time_spent_min` は本人がパネルで入れた値を使い、Claude が上書きしない。
会話の内容と `solved` が食い違うように見える場合（例：Claude の指摘で直したのに `自力AC`）は、
記録前に事実を示して本人に確認する。

### 6. 後片付け・要約提示
記録が済んだら `honban/.session.json` と `code_history_dir`（`honban/.history/<task_id>/`）を削除する
（同じ回を二重に記録しないため。途中のスナップショットはノートに残さない。最終コードは手順5で `<task>.<N>.cpp` に残してある）。
そのうえで、生成したレビュー本文と記録した内容を会話に要約して提示する。

## 注意

- レビューは「解いた後のメタ分析」であり、CLAUDE.md 目的#4 が禁じる
  「未解決問題への先回りヒント」ではない。両者を混同しない。
- 旧形式のノート（`felt` 行や単一の **考察ノート** 欄、本人と決めた **自分の考察** 欄を持つ回）は書き換えない。
  新しい回だけ新形式で書く。
