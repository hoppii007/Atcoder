# 本番レビュー → ノート記録

`honban/main.cpp` で解き終えた問題を、問題文・実装・考察ノート・難所を突き合わせてレビューし、
`problems/abcXXX/abcXXX_y.md` に **第N回** として記録する手続き。

前提となる仕様（ノート/タグのフォーマット、`solved` の定義、弱点分析の方針）は
プロジェクトルートの `CLAUDE.md` に従う。この skill はその「実行手順」を担う。

## トリガー

本人が「**終わりました。レビューして**」（同義の依頼を含む）と言ったとき、または `/honban-review`。
**それ以外のタイミングでレビューを先回りしない。**

## honban/main.cpp の構造

ファイル先頭にテンプレ（`// --- ここまでテンプレ ---` の行まで）があり、その下に
実際に解いた問題の**情報ブロック**（コメント）と `int main(){...}` 実装がある。情報ブロックの欄:

```
**どの問題?**   … ABC212E のような問題ID（これで対象ノートを特定する）
**difficulty**
**solved**      … 自力AC / 解説AC / 未AC（弱点分析の要）
**felt**        … 簡単 / 中 / 難しい
**考察ノート**
**難所**
## 問題全体のメモ
```

※ 問題タグ・つまずき分類タグは honban では書かない。どちらもレビュー時に AI が付ける（手順3）。

## 手順

### 1. 読む
`honban/main.cpp` を読み、情報ブロックの `どの問題?` から問題ID（例 ABC212E）を特定する。
difficulty / solved / felt / 考察ノート / 難所 / 問題全体のメモ と、`int main(){...}` の実装を取得する。
問題文は問題ID から URL（`https://atcoder.jp/contests/abc212/tasks/abc212_e` の形）を組み立て、
**WebFetch で問題ページを取得**する。レビューのために制約・入出力を確認するのに加え、
**新規ノートを作る場合（手順4）は問題文・制約の記入に使う**ので、この段階で必ず取得しておく。

### 2. レビューを書く（4点必須）
問題文・実装・考察ノート・難所を突き合わせ、次の4点を必ず含める:

1. **考察ノートの評価** — 言語化が十分か、鍵となる制約・語句を捉えているか（CLAUDE.md 目的#3）。
   薄ければ具体的に何を補うべきか。
2. **弱点・思考の癖の指摘** — 難所/つまずきを過去ノートの記録と突き合わせ、繰り返し現れる
   弱点パターンとして言語化する（目的#1）。根拠となるノートを示す。
3. **別解・より良い方針** — 想定解や、よりシンプル/高速な別解があれば提示。
4. **実装の正しさ・計算量** — `int main` を読み、バグ・エッジケース・計算量・可読性を指摘。
   問題なければ「問題なし」と明記。

印象論・励まし・主観的コメントは書かない。事実と、そこから論理的に導ける指摘のみ。

### 3. タグを付ける（2軸）

**(a) 問題タグ（frontmatter `tags` / 問題レベル）** — 本人が honban ブロックに書いた仮タグを
**素材**として、問題文・実装・想定解から**正式な問題タグを AI が付与する**。手法・データ構造・
考察パターンを表すタグを選び、`confidence` も判定する（典型なら `確定`、要確認なら `候補`）。
`tags.md`「問題タグ」表に無い語を使ったら、**必ず定義を1行追記**する（CLAUDE.md §3 の運用）。
- 新規ノート: AI が付けた tags / confidence を frontmatter に書く。
- 再挑戦（既存ノート）: 問題タグは問題レベルで固定。基本は維持し、明らかな誤り・不足のみ
  更新して、変更点は会話で根拠つきに述べる。無闇に付け替えない。

**(b) つまずき分類タグ（各回 `つまずき分類:` / 回レベル）** — その回の難所/考察から、
**`tags.md`「つまずき分類タグ」の統制語彙**の中で該当するものを選んで配列で付ける。
詰まり無し（自力で滞りなく解けた回）は `[]`。**この語彙は勝手に増やさない** ——
既存語で表せない詰まりが繰り返し出たときだけ、根拠つきで tags.md に1行追加する。

### 4. ノートに記録する
`problems/abcXXX/abcXXX_y.md` を開く（無ければ `problems/_template.md` を基に新規作成）。

**新規作成時は「## 問題」セクションを自動で埋める**（問題レベルで固定の情報）。手順1で WebFetch した
問題ページから、問題文の本文（または元の意味を損なわない忠実な要約）・入出力の形式・制約を転記する。
制約は考察の鍵になるので `N ≤ 10^5` のように原文に忠実に列挙する。取得に失敗したら空欄にせず、
その旨を会話で伝えて手動補完を促す。**再挑戦（既存ノートへの第N回追記）では「## 問題」は書き換えない。**

既存の `### 第N回` を数えて **次の回** として末尾に追記する（古い回が上・新しい回が下）。
1回分のエントリに含めるもの:

- `solved` / `felt` / `time_spent_min` / `つまずき分類`（手順3(b) で決めた配列）
  （**`solved` と `felt` が honban ブロックで埋まっていない場合は、記録前に必ず本人に質問して埋める**。
  憶測で断定しない。その他の項目は honban ブロックに無ければ空欄のままでよい）
- **考察ノート** / **難所**（honban ブロックの内容を転記。明らかな誤字は直し、直した旨を会話で伝える）
- **レビュー(LLM)**（手順2で書いたレビュー本文）

### 5. 会話に要約提示
記録後、生成したレビュー本文を会話にも要約して提示する。

## 注意

- `solved`（弱点分析の要・目的#1）と `felt`（体感難易度）は、honban ブロックで空なら
  **憶測で断定せず、記録前に必ず本人へ質問して確定させる**。両方揃ってから第N回を記録する。
- レビューは「解いた後のメタ分析」であり、CLAUDE.md 目的#4 が禁じる
  「未解決問題への先回りヒント」ではない。両者を混同しない。
